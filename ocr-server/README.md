# 카드영수증 OCR 판독 서버 (dtid-receipt-ocr-server)

반값여행 정산 증빙(카드 매출전표)을 서버에서 판독·대조하는 모듈입니다.
시험 페이지(dgtour 시안 A~G)가 브라우저에서 하던 판독을 그대로 서버로 옮겼고, 국세청 인증키를 서버에만 둘 수 있게 했습니다.

## 하는 일

| 항목 | 내용 |
|---|---|
| OCR | Tesseract.js 5 (kor+eng). 1차 원본 → 빠진 항목이 있으면 2차(폭 1800px·흑백·대비 강화) |
| 추출 필드 | 가맹점명, 결제지역(시군구·읍면동), 카드번호(마스킹 포함), 승인번호, 금액, 결제일, 비카드 전표(현금영수증·간이영수증·계좌이체·멤버십) 식별 |
| 사업자등록번호 | ① 체크섬 통과분만 인정 ② 번호 앞 라벨로 판별(사업자 라벨 채택 / 가맹점번호·TID·승인·전표·일시 뒤 숫자 제외) ③ OCR 오독 보정 ④ 체크섬이 틀린 번호는 한 자리 보정 후보를 국세청 조회로 가려 **하나만 남을 때만** 확정 |
| 국세청 상태조회 | 계속·휴업·폐업, 결제일 기준 폐업 여부. 공공데이터포털 「국세청_사업자등록정보 진위확인 및 상태조회 서비스」 |
| 제출 판정 | 입력값(카드·승인·금액·결제일·지역) 대조 + 사업자번호 판정(아래 표) |

### 사업자번호 판정

| 상황 | 결과 |
|---|---|
| 체크섬·국세청 통과, 결제일에 영업 중(결제 후 폐업 포함) | 통과 |
| 번호를 못 읽음 / 후보가 여럿 / 국세청 미등록 / 결제일 이전 폐업 — **1번째 업로드** | `RETAKE` — "사진이 선명하지 않습니다. 다시 촬영하여 업로드해주시기 바랍니다." |
| 같은 상황 — **2번째 업로드부터** | 통과 + `notes` 에 "사업자번호 확인 필요(담당자가 원본 확인)" — 정당한 신청이 막히지 않게 |
| 휴업 / 국세청 조회 실패 | 통과 + 담당자 확인 메모 |
| 인증키 미설정 | 체크섬까지만 확인, "국세청 미조회" 메모 |

### 실측 정확도 (카드영수증 111장, 정답 = Claude 판독 + 국세청 조회로 확정)

| 구분 | 장수 | 맞힘 | 못 찾음(재촬영 안내) | 같은 영수증의 다른 사업자 | **틀린 번호로 통과** |
|---|---|---|---|---|---|
| 휴대폰 사진(Sheet1) | 71 | 55 | 16 | 0 | **0** |
| 작게 잘린 캡처(횡성) | 40 | 16 | 23 | 1 | **0** |
| 합계 | 111 | **71 (64%)** | 39 (35%) | 1 | **0** |

- 판독 시간: 장당 중앙값 약 21초(CPU 1코어), 크고 흐린 사진은 최대 약 6분 → `OCR_TIMEOUT_MS`(기본 120초)를 넘으면 '판독 불가'로 돌려 재촬영 안내
- 같은 엔진을 쓰는 브라우저 시안(텍스트 기준 재현)도 72장 판독·오판 0건으로 비슷하다
- 시험 중 잡은 오판 3건은 규칙으로 막았다: 두 줄 잇기로 만들어진 남의 등록 번호, 국세청 조회 일시 실패로 통과된 오독 번호, 오독 번호가 우연히 다른 폐업 사업자와 맞아 정상 영수증이 반려될 뻔한 건
- **남는 위험**: 오독한 번호가 우연히 다른 사업자의 '영업 중' 번호와 맞으면 통과된다. 국세청 상태조회는 상호를 돌려주지 않아 막을 수 없다(111장 중 등록 번호와 맞은 오독 2건은 모두 폐업자였음). 상호까지 맞추려면 대표자명·개업일로 진위확인 API 를 써야 하는데 영수증에 개업일이 없다.

못 읽는 이유는 대부분 사진 품질입니다(흐린 감열지, 작게 잘린 캡처, 파란 잉크). Tesseract 가 한글 라벨과 숫자를 함께 뭉개는 경우가 많아 규칙만으로는 한계가 있습니다. 더 높은 인식률이 필요하면 `lib/ocr.js` 의 `recognize()` 를 영수증 특화 상용 OCR 이나 이미지 인식 AI 로 바꾸면 됩니다 — 나머지(필드 추출·사업자번호·국세청·판정)는 텍스트만 받으면 그대로 동작합니다.

## 동작 원리

### 1. 전체 흐름

```
영수증 이미지
  │
  ├─①  OCR 1차 ── 원본(EXIF 회전 반영, 긴 변 2400px 이하) → 글자 원문
  │      └ 날짜·승인번호·카드번호·금액·사업자번호 중 하나라도 빠지면
  ├─②  OCR 2차 ── 폭 1800px · 흑백 · 대비 1.6배 → 빈 항목만 채움
  │
  ├─③  필드 추출 ── 줄 단위로 라벨(카드·승인·금액·일시·상호·주소)을 찾아 값을 읽음
  ├─④  사업자번호 추출 ── 체크섬 + 라벨 '주인' 판별 + 오독 보정  (아래 2·3)
  ├─⑤  (못 찾으면) 한 자리 보정 후보 → 국세청 일괄 조회 → 등록 번호가 1개일 때만 확정
  ├─⑥  국세청 상태조회 ── 계속 / 휴업 / 폐업(폐업일)
  │
  └─⑦  제출 판정 ── 입력값 대조 → 결제지역 → 사업자번호 판정(재촬영·반려·담당자 확인)
```

이미지는 ①②에서만 쓰고 ③부터는 글자 원문만 다룹니다. 그래서 OCR 엔진만 바꿔 끼우면 나머지는 그대로 씁니다.

### 2. 사업자등록번호 체크섬 (국세청 검증식)

사업자등록번호 10자리 중 **마지막 자리는 앞 9자리로 계산한 검증 숫자**입니다.

1. 앞 9자리에 가중치 `1 3 7 1 3 7 1 3 5` 를 자리마다 곱해 더한다
2. 9번째 자리 × 5 의 **십의 자리**를 한 번 더 더한다
3. `(10 − 합계의 일의 자리)` 의 일의 자리 = 10번째 자리여야 한다

예) `123-45-6789?` → 1·1 + 2·3 + 3·7 + 4·1 + 5·3 + 6·7 + 7·1 + 8·3 + 9·5 = 165, 9×5=45 → 4 더해 169 → 10−9 = **1** → `123-45-67891`

- 무작위 10자리가 우연히 맞을 확률은 약 10% → 영수증의 다른 10자리 숫자(가맹점번호·TID·전표번호)는 대부분 여기서 걸러진다.
- 첫 세 자리는 세무서 코드라 0으로 시작하지 않고, 가운데 두 자리는 00이 아니다 → 이것도 거른다.
- **체크섬은 "틀렸다"만 알려주고 "어느 자리가 틀렸는지"는 모른다.** 한 자리만 바꿔 맞는 번호가 보통 9~10개 나온다. 그래서 ⑤에서 국세청 조회로 실제 등록 번호를 가린다.

### 3. 영수증에서 사업자번호를 고르는 법

영수증에는 10자리 숫자가 여러 개 있습니다(사업자번호, 카드사 가맹점번호, 단말기 TID, 전표번호, 전화번호). Claude 가 실제 영수증 111장을 판독할 때 쓴 방법을 규칙으로 옮겼습니다.

**(1) 번호의 '주인'은 바로 앞 라벨이다**
한 줄에 라벨이 여럿 있으면, 숫자 앞에 가장 가까이 있는 라벨이 그 숫자의 정체입니다.
- `사업자번호: 123-45-67891` → 채택
- `가맹점번호: 0123456789`, `TID: …`, `승인번호 …`, `전표No …`, `거래일시 26-10-01 12:00 …` 뒤의 숫자 → 버림
- `123-45-67891 / TID: 1234567 / TEL …` → 번호가 TID **앞**에 있으므로 채택 (줄 전체를 버리면 안 됨)

**(2) 점수** — 가장 높은 후보를 고른다(1점 미만은 버림)

| 근거 | 점수 |
|---|---|
| 앞 라벨이 '사업자·등록번호' | +2 |
| 윗줄에 '사업자' 라벨만 있고 숫자가 이 줄에 내려옴 | +1.5 |
| 상호·대표자·TEL 줄, `[123-…]` 처럼 괄호 안 | +0.5 |
| 형식 `ddd-dd-ddddd` | +1.5 |
| 붙은 10자리 | +1 |
| 띄어쓰기를 붙여야 10자리가 됨 (라벨 줄에서만 허용) | 0 |
| 오독 보정을 거쳐야 맞음 | −0.3 |

Tesseract 는 한글 라벨을 자주 뭉갭니다(예: '사업자번호'를 엉뚱한 글자로). 그래서 라벨이 없어도 **하이픈 형식**만으로 통과할 수 있게 했고, 대신 하이픈 없는 숫자는 라벨이 있어야 높은 점수를 받습니다.

**(3) OCR 오독 보정** — 숫자·구분자 사이에 끼어든 글자만 바꿔 본다. 보정한 결과도 체크섬을 통과해야 한다.

| OCR 이 읽은 것 | 보정 |
|---|---|
| `•` `·` `~` `.` 공백 | 구분자 `-` 로 인정 |
| 숫자 사이 공백 `1 23-45-67 8 91` | 붙여 봄 |
| `O` `o` `D` `Q` / `()` `口` | 0 |
| `I` `l` `\|` `!` | 1 |
| `S` → 5, `B` → 8, `Z` → 2, `G` → 6 | |
| 한글 `이` (숫자 사이) | `01` |
| 두 줄로 나뉜 번호 `123-45-678` / `91` | 이어 붙여 봄 |
| 라벨 글자가 숫자로 읽혀 11~12자리 | 10자리 창을 밀어 봄(라벨 줄에서만) |

### 4. 흐린 번호 보정과 국세청 조회 (⑤)

체크섬이 틀린 '거의 맞는' 번호(하이픈 형식이거나 사업자 라벨 줄)가 있으면 한 자리씩 바꿔 체크섬이 맞는 후보를 만들고(번호당 약 10개), 국세청에 한 번에 조회합니다(최대 100개).

- 등록된 번호가 **정확히 1개** → 그 번호로 확정 ("흐린 자리 보정")
- **2개 이상** → 확정하지 않음 → 재촬영 안내. 실측에서 후보 4개가 모두 등록 번호인 경우가 있었습니다 — "가장 그럴듯한 숫자"로 고르면 **남의 가게 번호로 통과**될 수 있어 막았습니다.

### 5. 국세청 상태와 결제일

| 국세청 응답 | 해석 |
|---|---|
| 계속사업자 | 통과 |
| 폐업자, 폐업일 > 결제일 | 결제할 때는 영업 중 → 통과 (옛 영수증에서 흔함) |
| 폐업자, 폐업일 ≤ 결제일 | 폐업 뒤 발행된 영수증이거나 **오독 번호가 우연히 다른 폐업 사업자와 맞은 것**(실측 1건) → 바로 반려하지 않고 재촬영 안내 → 2회차는 담당자 확인 |
| 폐업자, 결제일을 못 읽음 | "결제일과 비교 필요"로 표시, 판정은 입력한 결제일로 |
| 휴업자 | 통과 + 담당자 확인 (조회 시점 기준이라 결제일에 휴업이었는지는 모름) |
| 미등록 | 잘못 읽었거나(체크섬이 우연히 맞음) 위조 → 재촬영 안내 |

### 6. 재촬영 → 담당자 확인

판독 불가·후보 여럿·미등록이면 1번째는 "사진이 선명하지 않습니다. 다시 촬영하여 업로드해주시기 바랍니다."를 보여 주고, 2번째부터는 제출을 받되 "사업자번호 확인 필요"를 남깁니다.
작게 잘린 캡처나 처음부터 번호가 잘못 인쇄된 영수증은 다시 찍어도 같기 때문입니다. 서버는 상태를 저장하지 않으므로 몇 번째 시도인지(`attempt`)는 호출하는 쪽이 넘깁니다.

## 설치·실행

Node.js 18 이상.

```bash
npm install
npm test                                  # 규칙 단위 시험 (가상 번호만 사용)
NTS_SERVICE_KEY=발급받은_Decoding_키 npm start    # http://localhost:8080
```

Windows PowerShell: `$env:NTS_SERVICE_KEY='키'; npm start`

Docker: `docker build -t receipt-ocr . && docker run -p 8080:8080 -e NTS_SERVICE_KEY=키 receipt-ocr`

### 환경변수

| 이름 | 기본값 | 설명 |
|---|---|---|
| `PORT` | 8080 | |
| `NTS_SERVICE_KEY` | (없음) | 국세청 상태조회 인증키(공공데이터포털 **Decoding** 키). 없으면 체크섬까지만 |
| `ALLOWED_ORIGINS` | (없음) | 브라우저에서 직접 부를 도메인(쉼표 구분). 비우면 CORS 헤더를 내지 않음 |
| `OCR_WORKERS` | 2 | 동시 판독 수. 판독 1장에 CPU 1코어·약 10~25초 |
| `OCR_LANG` | kor+eng | |
| `OCR_LANG_PATH` | (CDN) | 언어 데이터 위치 — 폐쇄망이면 로컬 폴더 |
| `OCR_CACHE_PATH` | 실행 폴더 | 내려받은 언어 데이터 보관 위치 |
| `OCR_TIMEOUT_MS` | 120000 | 판독 시간 제한. 넘으면 '판독 불가'(재촬영 안내) |
| `MAX_BODY_MB` | 15 | 업로드 최대 크기 |

### 폐쇄망 설치

처음 실행할 때 Tesseract 언어 데이터(`kor.traineddata.gz`, `eng.traineddata.gz`)를 CDN 에서 내려받아 `OCR_CACHE_PATH` 에 저장합니다.
인터넷이 되는 PC 에서 한 번 실행해 생긴 두 파일을 서버의 폴더에 복사하고 `OCR_LANG_PATH` 를 그 폴더로 지정하면 됩니다.
국세청 조회는 `api.odcloud.kr` 로 나가는 HTTPS 가 열려 있어야 합니다(막혀 있으면 체크섬까지만).

## API

### `POST /api/receipt/analyze`
본문: 이미지 원본(`Content-Type: image/jpeg` 등) 또는 JSON `{"image":"base64 또는 data URL","payDate":"2026-10-01"}`.
쿼리 `?payDate=` 로 결제일을 주면 폐업일 비교에 씁니다.

```json
{
  "fields": { "shop": "○○식당", "region": "횡성군 우천면", "card": "1234-56**-****-3456",
              "approval": "12345678", "amounts": ["30000"], "date": "2026-10-01", "nonCard": null },
  "bizno": { "state": "found", "no": "123-45-67891", "nts": { "reg": true, "cd": "01", "stt": "계속사업자", "tax": "...", "end": "" } },
  "biznoView": "123-45-67891 ✅ 국세청 계속사업자",
  "spend": { "result": "included", "cat": "음식", "label": "인정 항목 — 음식" },
  "confidence": 71, "passes": 2, "ms": 18342
}
```
`bizno.state`: `found` · `none`(못 읽음) · `ambiguous`(후보 여럿) · `unregistered`(국세청 미등록)

### `POST /api/receipt/verify`
```json
{ "analysis": { ...analyze 결과... },
  "input": { "card": "1234567890123456", "approval": "12345678", "amount": 30000, "date": "2026-10-01", "region": "횡성" },
  "attempt": 1 }
```
응답 `{ ok, code, errors[], notes[], retake?, message?, bizno }` — `code`: `OK` · `MISMATCH` · `NON_CARD` · `REGION` · `RETAKE` · `EXCLUDED_BIZ`.
`attempt` 는 같은 증빙을 몇 번째 올렸는지(호출하는 쪽이 셉니다 — 서버는 상태를 저장하지 않음).

### `POST /api/bizno/status`
`{"b_no":["1234567891", ...]}` (최대 100개) → 국세청 조회 결과. 웹 화면이 인증키 없이 서버를 거쳐 조회할 때 씁니다.

### 그 밖
- `GET /health` → `{ok, nts}`
- `GET /` → 시험 화면(업로드 → 판독 → 입력값 대조)
- CLI: `node cli.js 영수증.jpg [--date 2026-10-01] [--raw]`
- 정확도 측정: `node tools/eval-folder.js <이미지 폴더> <정답.csv> [결과.csv]`

## 보안·개인정보

- 이미지는 메모리에서만 쓰고 디스크에 저장하지 않습니다. 오류 로그에는 경로와 메시지만 남깁니다.
- 인증키는 환경변수로만 받습니다. 코드·설정 파일·로그에 넣지 마세요.
- 국세청으로 나가는 값은 가맹점 사업자번호뿐입니다(카드번호·승인번호는 보내지 않음).
- 운영 시 앞단(리버스 프록시)에서 인증·요청 수 제한을 거세요.

## 규칙 동기화
